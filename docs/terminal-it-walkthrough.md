# 从终端 IT 的业务需求出发：语义层究竟怎么建，建完得到什么

本文使用虚构的终端零售与售后场景，解释 IT 团队如何实施。**不描述任何企业的实际系统、数据、流程与部署。** 厂商操作参考公开文档；示例业务规则由本仓库构造，厂商配置未在对应产品中部署验证。

如果主要消费者是 Agent，先读 [Agent 数据服务与 Ossie / OSI](agent-data-and-ossie.md)，再用本文了解底层业务模型的建设。

## 1. 先看最终交付物

假设你负责多个业务应用的数据供给。业务提出：

> 我想按区域、门店、机型看净销售额；后续还想结合库存和售后判断异常。

首期应交付一个可使用的“终端销售分析”数据产品，具体包含：

| 交付物 | 用户实际看到或使用的东西 | 谁负责建设 |
| --- | --- | --- |
| 统一的数据基础 | 订单行、退款、商品、门店等经过对齐的数据集 | 数据工程与应用接口团队 |
| 可执行的语义模型 | 可选择的“净销售额、机型、区域、销售月份”等字段，以及背后的计算关系 | 分析工程师 / 建模人员 |
| 消费入口 | 一个 Explore、共享语义模型、SQL 对象或 API | 数据平台与应用团队 |
| 授权规则 | 区域负责人只能消费其负责区域的数据 | 身份与数据权限团队 |
| 可查的口径和来源 | 净销售额怎么算、截至何时、使用哪个定义版本 | 业务负责人和数据负责人 |
| 验收与更新机制 | 与业务账表对账的样例、刷新计划、变更记录 | 上述团队共同负责 |

**建完之后，业务发出的是“按区域和机型查询净销售额”的请求，系统负责把这个请求翻译为正确的数据读取与计算。** 对业务而言，底层跨几个应用、退款存在哪张表，不应每次都重新理解。

实体详情消费也是一种结果：应用可能请求“这台设备关联的销售、激活、维修记录”。这与聚合指标不同，后文单独说明。

## 2. 第一步：从要支持的工作倒推范围

不要先接所有应用，也不要先建全公司的知识图谱。先确定消费任务与验收人：

| 消费者 | 首期请求 | 交付形式 | 暂不承诺 |
| --- | --- | --- | --- |
| 区域经营人员 | 按门店、机型、月份看净销售额 | BI 可拖拽分析 | 自动证明业绩变化的因果 |
| 业务门户 | 展示当前授权区域的经营数据 | 受控查询接口 | 任意访问所有原始表 |
| 数据分析人员 | 用统一销售数据做专项分析 | SQL / 数据服务 | 随意混用销售与财务口径 |
| AI 助手 | “上月哪些机型净销售额下降？” | 语义发现与查询工具 | 无依据地创建新指标 |

本例首期只实现销售与退款。库存、售后属于后续增量范围。先明确这些边界，才能知道字段、实时性、权限和预算应该如何设计。

## 3. 第二步：拿到各应用能提供的数据

下面都是假设的源系统，不指定 SAP、CRM 品牌或厂商：

| 数据提供方 | 可提供的数据 | 关键问题 |
| --- | --- | --- |
| 订单应用 | 订单行、成交金额、销售状态、SKU、门店 | 状态怎样变更？取消单是否还保留？ |
| 退款应用 | 退款单、退款金额、状态、原订单行 | 能否准确分摊到订单行？ |
| 商品主数据 | SKU、机型、颜色、容量、分类 | 不同应用编码能否统一？ |
| 门店 / 组织应用 | 门店、渠道、区域、组织有效期 | 区域调整后历史销售归谁？ |
| 库存应用 | 仓库—SKU—时点库存 | 是当前快照还是库存事件？ |
| 售后应用 | 工单、设备标识、故障、结案状态 | 能否关联到设备与原销售？ |

接入方式可以是现有数仓表、受支持的数据导出、应用 API 或变更同步。应用连接器、同步任务和清洗任务解决的是**如何持续获取可信数据**。语义模型依赖这些数据，但不会凭字段名自动解决主数据冲突或缺失业务关联。

如果已有可用数仓，应复用其中的可信数据集；不需要为语义层再搬一遍全部数据。是否物理汇聚或使用虚拟视图取决于现有平台与性能要求。

## 4. 第三步：把系统字段对齐为业务对象

最先要确定每张数据集“一行代表什么”。

| 业务对象 | 一行的粒度 | 稳定标识 | 典型关系 |
| --- | --- | --- | --- |
| 商品 SKU | 一种可售卖规格 | 统一 SKU ID | 多个 SKU 属于同一机型 |
| 门店 | 一家门店 | 统一门店 ID | 门店属于区域，可能随时间改变 |
| 销售订单行 | 某订单的一条商品行 | 订单行 ID | 指向一个 SKU、一个门店 |
| 退款记录 | 一次已记录退款 | 退款记录 ID | 多次退款可对应同一订单行 |
| 库存快照 | 某时点、仓库、SKU 的余额 | 时点 + 仓库 + SKU | 可与 SKU 对齐，不能跨日期直接累计 |
| 售后工单 | 一次服务事件 | 工单 ID | 多个工单可能对应同一设备 |

例如订单里的 `item_code=A123` 与售后的 `product_code=P009` 可能属于同一机型，却未必是同一 SKU。应建立经过验证的编码映射，保留匹配依据和未匹配记录，不能直接按名称相似度当成主键关联。

建议形成的准备层资产：

```text
dim_product       SKU → 机型 / 品类
dim_store         门店 → 区域 / 渠道
fct_sale_line     一行一条有效销售订单行
fct_refund        一行一次有效退款
mart_sale_line    退款归集后的订单行，用于首期分析
```

这些表名是示例。数据准备可以物化为表，也可以是受控视图；关键在粒度、映射和更新行为，不在表名前缀。

## 5. 第四步：把业务约定写清楚，再变成计算

本例用“净销售额”而非“财务确认收入”，避免把经营口径误称会计口径。假定业务确认：

| 要确认的事项 | 本例选择 |
| --- | --- |
| 销售范围 | 仅已完成销售，排除取消单 |
| 金额 | 已折扣后的商品行成交额，统一为人民币 |
| 退款范围 | 只扣已成功的退款，排除申请中退款 |
| 时间归属 | 按原销售日期归属，后发生退款回溯原销售期间 |
| 查询截止 | 只纳入数据截止时点前发生的有效事件 |
| 区域 | 本演示门店归属固定；生产需明确历史归属 |
| 计算 | 净销售额 = 有效销售额 − 已归集的有效退款额 |

这只是一个可验收的示例口径。若业务要“本月销售减本月发生退款”，应创建另一个有清晰名称的指标，而不是悄悄更改日期字段。

计算过程中最容易错的是一对多关联。某条销售金额 200 元，退款两次分别 10 元和 20 元，正确净额 170 元。如果连接明细后直接求和，会把销售额算成 400 元，得到错误净额 370 元。

首期可以先把退款按订单行汇总，再形成 `mart_sale_line`。这是一种容易核验的实现，不代表每个厂商都必须提前做宽表；支持正确关联规划的引擎可以在查询时处理。

### 可实际运行的小例子

仓库提供了 [SQLite 示例](../examples/terminal-sales/README.md)。只需 Python 标准库，不连接任何企业系统：

```bash
python examples/terminal-sales/run.py
```

它从虚构销售、退款、商品和门店数据生成准备层视图，再展示：

| 区域 | 机型 | 净销售额（元） |
| --- | --- | ---: |
| East | Model-A | 170 |
| East | Model-B | 300 |
| West | Model-A | 120 |

公司合计 590 元，East 合计 470 元。示例还验证申请中退款、取消销售和截止时间后的退款不会进入本例结果。**这是对数据准备与计算口径的验证，尚不是带认证、权限和查询 API 的生产语义服务。**

## 6. 第五步：在厂商产品里真正创建什么

下面四条是同一业务需求的不同实施路线，通常不需要全部购买或同时建设。

### 路线 A：使用 Looker，交付可探索的分析模型

你要做的事：

1. 在 Looker 配置到分析数据库的连接，使其能读取准备层。
2. 创建 LookML 项目，把订单行映射为 View，定义订单行主键、机型、区域、日期和净销售额。
3. 在 Model 中创建 Explore；如果维表未提前连接，则明确加入产品、门店关联及基数。
4. 在 Explore 验证“区域 + 机型 + 净销售额”的结果；配置访问规则并以实际用户测试。
5. 将项目验证、发布，业务人员使用 Explore 或基于它制作报表。

官方有从创建 Model、View 到 Explore 测试的操作教程。[LookML 建模教程](https://docs.cloud.google.com/looker/docs/looker-core-qs-model-data)

下面展示核心文件内容，连接名须替换，权限和上线配置未包含。它是说明性配置，未在 Looker 验证：

```lookml
# terminal_sales.view.lkml
view: terminal_sales {
  sql_table_name: mart_sale_line ;;
  dimension: sale_line_id {
    primary_key: yes
    type: string
    sql: ${TABLE}.sale_line_id ;;
  }
  dimension: region { type: string sql: ${TABLE}.region ;; }
  dimension: model_name { type: string sql: ${TABLE}.model_name ;; }
  measure: net_sales {
    type: sum
    sql: ${TABLE}.net_amount_cents / 100.0 ;;
    label: "净销售额"
  }
}

# terminal.model.lkml
connection: "your_analytics_connection"
include: "*.view.lkml"
explore: terminal_sales {}
```

这种结构对应官方的 Model / View / Explore 示例。[LookML 代码结构](https://docs.cloud.google.com/looker/docs/what-is-lookml)

**完成后得到什么。** 数据库中已有业务数据，Git 中新增可执行的模型文件，Looker 中新增分析入口。业务人员点选字段，Looker 生成 SQL 执行；其他报表复用该模型。接通数据库只完成第 1 步，不等于已有净销售额语义。

### 路线 B：使用 Power BI，交付共享语义模型

你要做的事：

1. 导入或连接准备层订单行、商品、门店、日期表；选择与环境匹配的存储模式。
2. 在模型视图中建立明确的一对多关系，检查过滤方向和日期关联。
3. 定义 DAX 度量，例如准备层已经正确归集退款时：`净销售额 = DIVIDE(SUM(mart_sale_line[net_amount_cents]), 100)`。
4. 配置组织到门店的访问映射、RLS 和刷新；在不同角色下核验结果。
5. 发布共享语义模型。后续报表连接该模型，避免每份报表复制一套公式。

关系、度量和发布的机制见 [星型模型指南](https://learn.microsoft.com/en-us/power-bi/guidance/star-schema/) 与 [从原始数据到共享应用的教程](https://learn.microsoft.com/power-bi/create-reports/tutorial-end-to-end-power-bi)。

**完成后得到什么。** 一个包含表、关系、度量和权限的 Power BI Semantic Model。多个报表与受支持的 Excel 分析使用它。要让自研应用或 Agent 使用，还需接入实际支持的模型查询方式；不能假设它自动变成任意业务 REST API。

**与上一步宽表的差别。** 宽表存的是数据；共享模型定义如何筛选、聚合、显示和授权。即使某些计算已经在准备层完成，也需要明确唯一维护位置，避免报表重复改变计算。

### 路线 C：使用 Snowflake，交付数据库原生的语义对象

你要做的事：

1. 将准备层放在可访问的 Snowflake schema。
2. 在 Semantic Studio 或 SQL 中创建 Semantic View，声明逻辑表、维度和指标。
3. 复杂模型再声明跨逻辑表关系；首期使用已经归集到订单行的准备层降低复杂度。
4. 验证查询、配置所需授权；若使用 Cortex，再补充业务说明、示例问题并单独评测。

以下 SQL 根据官方语法编写，需在实际账户校验表名、权限和支持版本，未在 Snowflake 执行：

```sql
CREATE SEMANTIC VIEW terminal_sales
  TABLES (
    sales AS mart_sale_line PRIMARY KEY (sale_line_id)
  )
  DIMENSIONS (
    sales.region AS region,
    sales.model_name AS model_name
  )
  METRICS (
    sales.net_sales AS SUM(net_amount_cents) / 100.0
  );

SELECT * FROM SEMANTIC_VIEW(
  terminal_sales
  DIMENSIONS sales.region, sales.model_name
  METRICS sales.net_sales
);
```

参考 [创建示例](https://docs.snowflake.com/en/en/user-guide/views-semantic/example) 和 [SQL 定义与查询语法](https://docs.snowflake.com/en/user-guide/views-semantic/sql)。

**完成后得到什么。** 数据库多了一个可管理、可查询的语义对象，而不只是普通表字段注释。消费者查询维度与指标；能否在具体 BI 中直接点选，取决于该工具的集成方式。Cortex 使用语义的路径也需要独立确认，不可由对象存在推定 AI 结果正确。

### 路线 D：使用 Palantir，交付可查询和操作的业务对象

如果需求进一步变成“查看一台设备关联的售后情况，并创建质量排查任务”，单纯净销售额指标不够。你需要建立具体对象和行为。

你要做的事：

1. 准备商品、设备、门店、销售、工单等稳定的数据集，明确设备标识与来源。
2. 在 Ontology Manager 新建对象类型，选 backing datasource，把稳定唯一字段设置为主键，把业务字段映射为属性。
3. 定义设备—SKU、设备—工单、销售—门店等关系；核验关联完整性。
4. 为需要的业务动作定义输入、校验、执行逻辑与授权，例如创建质量排查任务。
5. 保存并部署后，让业务应用或 Agent 使用对象查询与动作接口。

对象创建、数据源、主键和保存步骤见 [官方操作指南](https://www.palantir.com/docs/foundry/object-link-types/create-object-type)；动作与外部系统连接见 [Ontology 说明](https://www.palantir.com/docs/foundry/ontology)。

**完成后得到什么。** 系统里存在可定位的 Device、ServiceCase 等对象，以及经授权的操作。业务可以先找到某台设备，再沿关系查工单并执行流程。若要把任务写入现有工单系统，仍需实现其 API 集成和失败处理；创建对象模型不等于完成源系统写回。

## 7. 其余方案落在什么实施环节

这里将已有调研转换为建设动作，功能依据见 [厂商专题及引用](vendor-landscape.md)：

| 产品 | 你实际需要配置或开发 | 完成后的主要产物 |
| --- | --- | --- |
| dbt Semantic Layer | 在 dbt 数据模型上声明实体、维度、指标；部署模型并接下游接口 | 由 MetricFlow 规划的指标查询服务 |
| Cube | 配置数据源；定义 cubes、views、measures、joins、访问规则；按需做预聚合 | 供应用和 BI 消费的语义 API |
| AtScale | 建事实、维度与层级；发布模型；验证工具连接和聚合加速 | 多维分析模型与查询服务 |
| Databricks | 在 Unity Catalog 中创建 Metric View，定义维度和 measures；验证 SQL 与工具使用 | 可治理的指标对象 |
| Denodo | 创建源视图，整合成统一商品、门店等业务视图，再发布消费视图 | 跨源的逻辑业务数据接口 |
| SuperSonic | 接数据源并建指标、维度等语义模型；配置问数映射、权限并验证问题集 | Headless BI 查询入口与 Chat BI |
| DeepAnalyze | 配置模型与隔离执行环境，额外适配受治理数据接口 | 能执行分析任务的助手，不自动生成权威业务模型 |
| EvoOntology | 从数据和任务构建语义知识，保留映射、证据和版本，设置演进评估 | 可供 Agent 检索与更新的语义上下文 |

无论用哪个产品，“各应用的 SKU 是否为同一对象”“退款按什么日期归属”都必须有可信的确认机制。厂商提供表达和执行方式，企业补齐本企业的业务定义。

## 8. 建完到底能支持什么，差哪些条件

| 场景 | 已有销售语义模型能做什么 | 还需要什么 |
| --- | --- | --- |
| 经营看板 | 不同报表按同一口径展示净销售额 | BI 页面与刷新运维 |
| 自助分析 | 按已支持的区域、门店、机型切分 | 合法维度组合与性能验证 |
| 业务门户 | 消费统一指标结果 | API 适配、身份传递和应用开发 |
| AI 问数 | 将业务问题映射为已定义指标请求 | 语义检索、歧义澄清与评测 |
| 周报与变化解释 | 为统计和图表提供可信输入 | DeepAnalyze 等分析工具及解释验收 |
| 库存与销售对比 | 可复用 SKU、门店等共同维度 | 库存粒度、时点与可用量规则 |
| 售后发生率 | 可复用机型和设备标识 | 分子、分母、去重设备、观察窗口与激活队列 |
| 质量事件处置 | 可提供业务对象与证据 | 动作接口、审批、状态管理与写回 |

**销售表与售后表能连接，不代表就有“故障率”。** 如果同一台设备维修三次，工单数不能直接充当故障设备数；如果没有激活设备数和观察窗口，也无法凭销量算出可比较的设备故障率。此时应明确输出“售后工单量”或“缺少分母”，不要把联表成功包装成业务语义完整。

## 9. 一个 IT 团队可以据此安排的首期工作

| 工作 | 具体产物 | 完成标准 |
| --- | --- | --- |
| 业务确认 | 三个消费任务、五个关键口径、负责人 | 业务方能用样例确认预期值 |
| 数据接入 | 源表 / API 清单、同步方式、字段映射 | 数据可重复获取且有截止时间 |
| 对齐与准备 | SKU / 门店映射、订单行与退款处理 | 未匹配有记录，重复关联不放大金额 |
| 产品建模 | 选一种平台创建可执行模型 | 同一请求稳定返回正确结果 |
